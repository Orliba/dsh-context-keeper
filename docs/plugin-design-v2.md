# dsh-think-watch · 插件方案 v2

> 2026-10-28 晚修订。上一版（cot-warden-design.md）基于「检测浪费 → 降档/停轮」，
> 被真实数据否掉。这一版换成「规则前置 + 事后对账」。

---

## 一、上一版错在哪（先说清楚，不重复踩）

| 原本设想 | 实测结果 | 结论 |
|---|---|---|
| 检测绕圈子 → 降低档位 | 真实轨迹里没有可测的浪费（重复率 0.1%，跨步 0.3%，长尾都是有效工作） | 无靶可打 |
| 用 `agent/turn-stopping` 中途刹车 | 该钩子在 `turnEnds` 之后才触发（源码 `dsh-agent-loop` 确认） | 停不了，只能"不再开下一章" |
| 用 `llm/stream` 做旁路 | 全库无官方使用者，属未沉淀的内部钩子 | 不适合做地基 |

**根本原因**：把「思考质量」当成一个可以被事后检测、再被外部纠正的量。
实际上模型每次请求都是无状态的，外部无法"惩罚"它让它长记性。

---

## 二、新方案：三层，都在公开接口上

### L1 · 规则前置（核心，治本）

**问题**：模型不知道"这里该想多深"。

**做法**：通过 `ctx.systemPrompt.section()` 注册一个常驻段落，把预算规则写进系统提示。

```js
ctx.systemPrompt.section({
  name: 'think-watch:budget',
  order: 2500,              // 排在工具说明之前、策略段之后
  text: '<渲染出来的规则文本>',
  interpolate: false,
})
```

这个接口是**公开的**（有文档注释、有类型校验、返回可 dispose 的 effect），
不是内部钩子。段落注册/注销会自动发 `system-prompt/change` 事件。

**规则长什么样**（这是产品核心，要写得让模型能照做）：

```
## 思考预算

- 目标：在动手之前把关键判断定下来，不要一边做一边反复推翻。
- 动手前最多用 N 段讲清楚：要做什么、为什么、怎么验证。
- 一旦说出计划（"我打算…""Plan:"），后面就执行，不要重开计划。
- 真发现推翻了前面的结论，明确写"前面的判断错了，因为…"，然后只往前走一次。
- 只读探查类任务，思考可以短；涉及改动、且有不可逆风险的，值得多想。
```

**为什么这个有效**：它不依赖检测，也不存在"误判"。模型每轮都看得见，
自然地把"先定后做"当成默认行为。这就是用户说的「设了限度」，只是实现方式是**前置**而不是事后惩罚。

### L2 · 事后对账（可测、可查、零风险）

复用已完成的离线 CLI：会话结束后算它到底想了多少、在第几段定的计划、
定完之后有没有再反复。**只读，不干预。**

这一层是给 L1 提供证据的：
- 装了规则之后，`commit@` 位置是否前移
- `recommit` 次数是否下降
- 思考 token 占比是否变化

**这才是"长教训"的验收方式**——不是靠模型自己说，是靠数据对比。

### L3 · 显示（看得见）

在聊天界面思考内容上方挂一个徽章，显示本轮：思考 token、计划出现在第几段、是否反复。

挂载点：`conversation.chat.reasoning.body` 插槽（官方 CoT 翻译插件就是这么挂的，已验证）。

**这一层纯展示，不碰任何模型输入。**

## 三、为什么这样比原方案好

| | 原方案（检测→降档） | 新方案（规则前置→对账） |
|---|---|---|
| 依赖 | 未沉淀的内部钩子 | 公开的 `systemPrompt.section()` |
| 前提 | 假设能检测出"浪费" | 不需要检测，规则是确定的 |
| 误伤风险 | 降错档 = 思考质量真下降 | 规则写错才误伤，且可回滚 |
| 可验证 | 无对照 | 装/不装两组数据直接比 |
| 用户收益 | 省 token，但可能变笨 | 想得更结构化，且知道它想了多少 |

---

## 四、实施顺序

| 阶段 | 内容 | 依赖 | 可验证性 |
|---|---|---|---|
| **P1** | 规则段落插件（纯 host 侧，无 UI） | `systemPrompt.section()` | 装上前后的 `commit@` / `recommit` 对比 |
| **P2** | 统计工具：`think_watch` 工具 + 指标落盘 | 已有 CLI 逻辑 | 会话内能问「我这轮想得怎么样」 |
| **P3** | 思考徽章（client 侧 React） | `conversation.chat.reasoning.body` | 界面上看得见 |

**P1 就能产生价值**，P2/P3 是增强。
每一步都能单独安装、单独卸载、单独验证。

---

## 五、风险与回滚

| 风险 | 处置 |
|---|---|
| 规则段落写得太长，挤占上下文 | 硬限制字数（默认 ≤ 400 字），超了截断并告警 |
| 规则文本让模型过度规划 | `budget` 段落可配置为 `off`，一条 YAML 关掉 |
| `systemPrompt.section()` 未来改名 | 插件启动时探测该方法是否存在，不存在则降级为只做 L2/L3，**不崩** |
| 排序位置冲突 | 用 `getSectionOrder()` 拿官方序号，不硬编码 |

回滚：`cordis.patch.yml` 里把该 entry `disabled: true`，或直接卸包。
