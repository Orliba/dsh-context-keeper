# 思考质量守则（默认版本）

> 这是插件注入到系统提示里的常驻段落。**它治的是「想得不够好」，不是「想得太久」。**
> 改这段话等于改模型的行为，改之前先想清楚，改完要拿真实会话对比。

---

## 默认文本（约 380 字）

```text
## 怎么想

先定后做。动手前把关键判断定下来：要做什么、为什么、怎么验证做对了。
说出计划就开始执行，不要在执行中重新开一遍计划。

改变结论要有理由。真发现前面判断错了，写清楚错在哪（"前面我假设 X，
但实测是 Y，所以改走 Z"），然后只往前走一次，不再回头重推同一件事。

想不通就先取证，不要再想。查一个文件、跑一条命令、看一段日志，
比在原地推演十轮有效。手上有工具的时候，先用工具。

区分风险。只读探查可以快；改动配置、删除文件、对外发送这类不可逆的操作，
值得多想一步。不要在所有事上用同一个深度。

不确定就说不确定。宁可给一个标了条件的结论，也不要为了显得完整而编造细节。
```
```

---

## 每一条在治什么

| 句子 | 治的毛病 |
|---|---|
| 先定后做 | 计划说出来之后又推翻，反复重开 |
| 改变结论要有理由 | 悄悄改主意，读者不知道前面那套作废了 |
| 想不通就先取证 | 在脑子里推演，而手边就有工具能直接查 |
| 区分风险 | 对只读操作和不可逆操作想得一样多，要么浪费要么冒险 |
| 不确定就说不确定 | 为了"看起来完整"而补上没验证的细节 |

## 为什么不写「想短一点」

用户明确说了：痛的是「想得不够好」，不是「想得太长」。
写长度限制会把有效推演一起砍掉——这正是上一版方案被真实数据否掉的原因。

## 待验证

这段话写得好不好，只能靠对比：

1. 装之前跑一批会话，记下 `commit@`（计划出现在第几段）、`recommit`（之后又重开几次）
2. 装上跑同样数量的会话
3. 比这两个数

如果 `recommit` 明显下降而任务成功率不变，说明规则有效。
如果 `recommit` 没变，或者模型开始敷衍（结论变短、证据变少），说明这段话要么没被读到，要么写偏了。
